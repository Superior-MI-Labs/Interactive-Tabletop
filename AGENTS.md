# Interactive Tabletop — coding agent contract

**Project:** Local-first, early-alpha D&D tabletop with browser and Python desktop delivery, fillable-PDF import, physical dice, and player/DM-confirmed rules automation.

Start each task by checking current `main`, `VERSION`, relevant source/tests and [`PROJECT_HANDOFF.md`](PROJECT_HANDOFF.md). The handoff is a checkpoint, not proof that the repository has not changed. The user-facing copy/paste prompt lives in [`AI_START_HERE.md`](AI_START_HERE.md).

## State ownership — do not duplicate systems

- `web/` is the **only authored UI source**. `docs/` and desktop ZIPs are generated by `tools/build_site.py` and `tools/build_release.py`; never patch generated UI.
- `web/vault-store.js` persists characters, imported facts, resources and encounters. `web/character-import.js` normalizes D&D Beyond PDF fields across browser/desktop. No parallel character or resource store.
- `web/dnd-action.js` owns planning, eligibility, action economy, trigger evidence, event windows, workflows, turn/condition clocks and resource/effect commits. `web/app.js` owns presentation, confirmation and **transient dice**; never bypass the engine to mutate gameplay state.
- `web/dnd-2014-reference.json` plus `web/reference-catalog.js` provide edition-scoped, validated rules data. **Never execute mechanics inferred from descriptions, class/ability names, homebrew prose or imported text.** Unknown or unsupported rules remain manual and DM-confirmed.

## Approach each change as an architecture decision

1. Reproduce/trace existing behavior and find its owner and tests. Compare **extending/refactoring existing code** with **adding a subsystem**. Prefer the existing path; do not introduce a second source of truth.
2. Define prerequisites, actor/target identity, event timing, cost, cancellation/undo and rollback before implementing. Build a cohesive patch; no feature-specific workaround if a shared contract needs correction.
3. For gameplay work, read **relevant sections**, not the entire documentation tree: [`ARCHITECTURE.md`](ARCHITECTURE.md), [`RULESET_AUTOMATION_CONTRACT.md`](RULESET_AUTOMATION_CONTRACT.md), and [`DND_EFFECT_CAPABILITY_AUDIT.md`](DND_EFFECT_CAPABILITY_AUDIT.md) for qualified effects. `CHANGELOG.md` is historical.
4. Preserve existing and legacy vaults, correct 2014/2024 boundaries, explicit Auto/Guided/Manual behavior, and character-owned dice. Preparing or canceling a throw does not spend resources; a committed cost is not silently refunded.
5. Test positive and negative paths: stale/duplicate evidence, wrong actor/target, insufficient resources, skipped/undone turns, cross-character switching, cancellation, malformed legacy records, and pointer interactions where relevant.
6. If a requested feature requires guesses about untracked initiative or other rules, **challenge it**. Do not claim unsupported editions or full automation exist.

## Qualification and publication

```bash
python3 -m pip install -r tools/requirements-qa.txt
# If needed: python3 -m playwright install chromium
bash tools/qualify.sh
python3 tools/build_release.py
python3 tools/build_site.py
```

- `tools/qualify.sh` is the **single** Python, JavaScript and Chromium gate used in `.github/workflows/pages.yml`. Browser tests must use `tests/browser_support.py`; `TABLETOP_CHROMIUM=managed` selects managed Chromium. Keep `tests/test_qualification_contract.py` synchronized without hardcoding counts in these instructions.
- Never commit private PDFs, character saves, test screenshots/caches, generated ZIPs or manually changed Pages assets. Do not add dependencies or extra AI frameworks without an actual need.
- For application releases, update `VERSION`, `CHANGELOG.md`, relevant contracts and [`PROJECT_HANDOFF.md`](PROJECT_HANDOFF.md) in the same batch. Docs-only changes do not require a version bump.
- Commit/push **only when authorized**; inspect and preserve changes from other agents, never force-push. Report exact verification performed; **GitHub push, CI qualification and Pages deployment are separate states**. Do not claim success until each is verified.

**Keep this file short and version-neutral.** Architecture and rules detail belong in their respective contracts, release history in `CHANGELOG.md`, and current work in `PROJECT_HANDOFF.md`. Do not append a new AGENTS section for every patch.
